v8 Core Validation Architecture Review

Commit 1: canonical IDs, branded types, validation boundary, and testable domain isolation.

This document summarizes the current implementation strategy for the ID boundary and the validation model. The goal is to keep the domain clean, make parsing deterministic, and ensure every branded ID passes through one controlled boundary only.

Architecture Summary

unknown input Zod validation canonical format brandId() Domain ID

The ID pipeline is intentionally simple: external input enters as unknown, then passes structural validation, canonical ID format validation, and finally the controlled branding function.

Core Contract

unknown
  ↓
Zod / structural validation
  ↓
canonical ID format validation
  ↓
brandId()
  ↓
ParseResult<CaseId>
  ↓
Domain Entity

The important rule is that brandId() is not a validator. It is the last controlled boundary after validation already succeeded.

Success Criteria

  • CaseId, FactId, FactRecordId, and the other branded IDs are compile-time incompatible.
  • Invalid IDs are rejected at runtime.
  • Wrong prefixes are rejected.
  • Empty and whitespace-only IDs are rejected.
  • Canonical IDs parse deterministically.
  • parse → serialize → parse is stable.
  • No as CaseId outside the validation boundary.
  • The domain does not know Zod, React, or persistence.
  • Legacy IDs are handled only by migration logic, not by canonical parsing.
  • No RootState, reducer, or UI coupling yet.

Engineering Verdict

This is a clean and defensible design for a validation-heavy TypeScript application. It is especially good for teams that want explicit parsing boundaries, stable branded types, and a normalized state model that remains easy to audit.

For LinkedIn validation from engineers, this version works well because it is precise, short enough to scan, and structured enough to review technically.
